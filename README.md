# 칠갑산 석촌 햇 밤 — 무통장 입금 전용 밤 판매 사이트

충남 칠갑산 석촌에서 유기농 햇밤(대보·포르단·옥광)을 파는 1인 판매자용 사이트다.
카드 결제 없이 **무통장 입금만** 받고, 입금 확인을 **사람이 대조하지 않는다**.

운영자가 기술에 익숙하지 않다는 전제로 만들었다. 그래서 대부분의 설계가
"손이 덜 가는 쪽"이 아니라 **"틀렸을 때 손으로 수습할 일이 없는 쪽"** 으로 기울어 있다.

## 1. 어떻게 돌아가는가

### 입금이 자동으로 확인되는 흐름

```
손님 주문          아버지 폰                     서버
──────────         ──────────                    ──────────
주문서 작성   →    (입금대기 주문 생성)
계좌로 입금   →    은행 입금 문자 도착
                   MacroDroid가 문자를
                   **통째로** 전달
                          │
                          └─ POST /api/deposit ─→  문자에서 금액·이름·은행을 뽑고
                                                   입금대기 주문을 찾는다
                                                        │
                   알림으로 결과 표시  ←──────────────────┤
                                              이름·금액 둘 다 맞고 1건 → 발송확정
                                              둘 다 맞고 여러 건    → 확인필요
                                              한쪽만 맞음          → 확인필요
                                              둘 다 다름           → 미매칭 (알림 없음)
```

### 한쪽만 맞아도 사람에게 보인다

이름과 금액이 **둘 다** 맞아야 자동으로 발송대기가 된다. 하지만 **한쪽만 맞아도**
그냥 넘기지 않고 `확인필요` 로 올려 관리자 첫 화면 빨간 영역에 띄운다.

| 이름 | 금액 | 결과 | 폰 알림 |
|---|---|---|---|
| 맞음 | 맞음 | 1건이면 **발송확정**, 여러 건이면 **확인필요** | 온다 |
| 맞음 | 다름 | **확인필요** | 온다 |
| 다름 | 맞음 | **확인필요** | 온다 |
| 다름 | 다름 | **미매칭** — 맨 아래 참고 목록으로 | 안 온다 |

손님이 이름을 조금 다르게 적었거나(`김지수` ↔ `김지수님`) 금액을 잘못 보낸 경우가
실제로 있다. 그걸 미매칭으로 묻어 두면 **돈은 들어왔는데 아무도 모르는 상태**가 된다.
사람이 한 번 보면 될 일이라 위로 올린다.

> 두 건 값을 한 번에 보낸 합산 입금도 여기 걸린다(이름은 맞으므로).
> **어느 주문도 저절로 발송대기가 되지 않는 것**이 중요하다 — 한 건만 확정되면
> 나머지 한 건을 그냥 부치게 된다.

**문자 해석은 서버가 한다.** 폰은 받은 문자를 그대로 넘기기만 하므로
MacroDroid 설정에 정규식도 변수도 없다.

문자 형식은 은행마다 다르고 언제든 바뀐다. 해석 규칙을 폰에 두면 그때마다
아버지 폰을 직접 받아서 고쳐야 하지만, 서버에 두면 코드를 고쳐 배포하면 끝이다.
읽지 못한 문자는 원문이 관리자 화면에 남아 무엇 때문에 실패했는지 볼 수 있고,
`npm run sms` 로 실제 은행 문자를 넣어 규칙을 미리 검증할 수도 있다.


### 손대야 하는 것이 생기면 첫 화면에 뜬다

관리자 첫 화면(`/admin`)은 위에서부터 **급한 순서**로 쌓여 있다.

1. 🔴 **확인이 필요한 입금** — 같은 이름·금액의 주문이 여러 건이라 하나를 골라야 하는 건
2. 🟠 **매진** — 손님이 지금 주문할 수 없는 상품
3. 📦 **보낼 주문** — 송장번호 넣고 [발송완료] 누르면 끝
4. 📄 **기타 매칭되지 않은 문자** — 접혀 있다. 참고용

**미매칭은 맨 위에 올리지 않는다.** 아버지 개인 계좌라 가족 송금이나 다른 거래 문자가
섞여 들어오는데, 그것까지 빨간 영역에 쌓이면 정작 급한 확인필요가 묻힌다.
맨 아래 접이식 목록에 최신순으로 모아 두고, 궁금할 때만 편다.

> 혹시 진짜 손님 입금이 거기 있으면 **주문관리**에서 그 주문을 찾아 발송대기로 바꾸면 된다.

## 2. 로컬에서 돌려보기

Firestore 에뮬레이터를 쓰므로 **실제 데이터를 건드리지 않고 과금도 없다.**
(에뮬레이터에는 Java가 필요하다)

```bash
npm install
cp .env.local.example .env.local

npm run emulators   # 터미널 1 — Firestore 에뮬레이터
npm run seed        # 터미널 2 — 상품 18종 + 기본 설정 넣기
npm run dev         # http://localhost:3000
```

관리자 로그인 비밀번호는 `.env.local` 의 `ADMIN_PASSWORD` (기본 `test1234`).

```bash
npm run smoke   # 가격 재계산·입금 매칭·자동 정리·재고 복원 등 핵심 로직 193가지 점검
```

`npm run smoke` 는 에뮬레이터에서만 돌아간다(실 데이터 삭제 사고 방지).
주문/입금 컬렉션을 비우고 다시 채우므로 **운영 데이터에는 절대 쓰지 말 것.**

### 3-2. 시크릿 3개 등록

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

이후 `main` 에 push할 때마다 자동으로 빌드·배포된다.


### 3-5. 첫 데이터 넣기

방금 배포한 사이트는 Firestore가 비어 있어 손님 화면에 상품이 하나도 안 보인다.
**전부 `/admin` 화면 안에서 끝난다 — 명령어도 자격증명도 필요 없다.**

1. `/admin` 로그인 → **재고관리** 로 간다.
2. **새 그룹 만들기** 로 품종을 만들고(예: `대보`), 그 그룹에 상품을 넣는다

## 4. MacroDroid 설정 (아버지 폰)

이 부분이 사이트에서 가장 중요하다. 한 번 맞춰 놓으면 다시 손댈 일이 없다.
아래는 **MacroDroid v5.65.9** 화면 기준이다.

**폰은 문자를 통째로 보내기만 한다.** 금액과 이름을 뽑는 일은 서버가 한다.
그래서 폰에는 정규식도 변수도 없고, 은행이 바뀌어도 **아버지 폰을 다시 만질 필요가 없다**
— 서버 코드(`src/lib/sms.ts`)만 고쳐 배포하면 된다.

전체 그림은 이렇다.

```
은행 문자 도착
   ↓  발동(트리거) — 이 문자가 맞는지 거른다
   ↓  동작 1  HTTP 요청 — 문자를 통째로 서버에 보내고, 답을 기다렸다가 상자에 담는다
   ↓  동작 2  알림 표시 — 상자에 담긴 답을 띄운다  (안 해도 된다)
```

---

### 발동 (트리거) — 언제 매크로가 돌 것인가

MacroDroid 앱 → 아래 `+` → **매크로 추가** → 발동의 `+` → **연결** → **SMS 수신**

1. **번호 선택** → **번호 입력** 에 은행 문자가 오는 번호를 넣는다
2. **포함하면** 체크 → `입금` 입력 → **확인**

**왜 이렇게 하나**

두 가지를 겹쳐서 거른다. 은행 번호로 한 번, 문자 내용으로 한 번.

- **번호**로 거르지 않으면 광고 문자까지 서버로 날아간다.
- **`입금`** 으로 거르지 않으면 **출금** 문자도 함께 간다. 밤값이 나간 것도 아닌데
  서버가 이름과 금액을 뽑아 주문을 찾게 된다.

서버도 `입금` 이 없는 문자는 거부하지만, **폰에서 먼저 거르는 편이 낫다.**
쓸데없는 요청이 줄고 배터리도 덜 쓴다.

> 은행 번호는 문자 앱에서 은행 문자를 열어보면 위에 있다. (예: `15881111`)

---

### 동작 1 — HTTP 요청

동작의 `+` → **웹 접속** → **HTTP 요청**

#### ① 설정 탭

| 칸 | 값 |
|---|---|
| 요청 종류 | `POST` |
| URL 입력 | `https://albam.web.app/api/deposit` |
| ☑ **완료시까지 다음 동작으로 진행하지 않음** | **반드시 체크** |

**왜 POST 인가**

문자 전문을 **본문에 담아** 보내기 때문이다. GET은 주소 뒤에 값을 붙이는 방식이라
문자가 길거나 한글이 섞이면 잘리거나 깨진다. 문자 내용이 곧 우리가 읽을 원본이므로
한 글자도 변형되면 안 된다.

**"완료시까지 다음 동작으로 진행하지 않음" 을 꼭 켜야 하는 이유**

이걸 안 켜면 MacroDroid는 서버 답을 기다리지 않고 바로 다음 동작으로 넘어간다.
그러면 아래 ③에서 만든 상자에 **이번 답이 담기기 전에** 알림이 상자를 열어본다.
결과는 이렇게 된다.

```
첫 번째 입금  → 상자가 비어 있어 알림이 안 뜸
두 번째 입금  → 첫 번째 답이 뜸
세 번째 입금  → 두 번째 답이 뜸      ← 한 박자씩 밀린다
```

실제로 겪은 증상이다. 이 체크 하나로 해결된다.
(입금 처리 자체는 밀려도 정확했다 — 늦은 것은 알림 글자뿐이었다)

#### ② 응답 저장 — 설정 탭 아래쪽

**응답 저장** 에서 **`string형 변수에 HTTP 응답 저장`** 을 고른다.

그 아래 변수 선택 옆의 **`+`** → **전용 변수** 체크 → 이름은 `response`

**무엇을 하는 것인가**

서버는 처리 결과를 **한국어 한 줄**로 답한다.

```
✅ 발송확정: 김지수님 450,000원 → 발송대기 (옥광 대 10kg 5)
```

이 답을 어디에도 담아두지 않으면 그냥 버려진다. `response` 라는 이름의 상자에 담아 두면
다음 동작에서 꺼내 쓸 수 있다. **전용 변수**(지역 변수)는 이 매크로 안에서만 쓰는 상자라
다른 매크로와 이름이 부딪히지 않는다.

> 전용 변수의 매직 텍스트는 `[lv=response]` 다. 전역 변수로 만들었다면 `[v=response]`.

#### ③ Body 내용 탭

| 칸 | 값 |
|---|---|
| 컨텐츠 타입 | `application/json` |
| Body 내용 | **텍스트** 선택 |

아래 칸에 **한 줄로** 넣는다.

```
{"token":"등록한_MACRODROID_토큰","text":"[sms_message]"}
```

- `등록한_MACRODROID_토큰` 자리에는 `albam-macrodroid-token` 시크릿에 넣은 값을 적는다
  (6장 참고). **이 문서에 실제 값을 적지 말 것** — 저장소가 공개다.
- 중괄호 `{` 부터 `}` 까지 한 줄이다. 줄바꿈을 넣지 않는다.

**각 조각이 하는 일**

| 조각 | 하는 일 |
|---|---|
| `application/json` | "본문을 JSON으로 읽어라" 고 서버에 알린다. 이게 없으면 서버가 본문을 못 알아본다 |
| `token` | 아무나 가짜 입금을 보내 주문을 발송대기로 올리지 못하게 막는다 |
| `text` | 문자 **전문**. 서버가 여기서 금액·이름·은행을 뽑는다 |
| `[sms_message]` | MacroDroid 매직 텍스트. 보낼 때 방금 받은 문자 내용으로 바뀐다 |

`[sms_message]` 는 손으로 타이핑해도 되지만, 한 글자만 틀리면 문자 내용이 안 들어가고
`[sms_message]` 라는 **글자 그대로** 서버로 간다. 오른쪽 `...` 버튼으로 큰 편집창을 열고
**매직 텍스트 버튼**에서 골라 넣는 편이 안전하다.

다 넣었으면 오른쪽 위 **체크(✓)** 로 저장한다.

### 동작 2 — 알림 표시 (안 해도 된다)

동작의 `+` → **알림** → **알림 표시**

| 칸 | 값 |
|---|---|
| 제목 | `입금 확인` |
| 본문 | `[lv=response]` |

본문의 `[lv=response]` 는 **"response 상자에 든 것을 여기에 꺼내 놓아라"** 는 뜻이다.
동작 1에서 담은 서버 답이 그대로 알림에 뜬다.

**동작 순서가 중요하다.** 알림이 HTTP 요청보다 **위**에 있으면 담기지도 않은 빈 상자를
꺼내게 된다. 순서가 뒤바뀌었으면 동작을 길게 눌러 끌어서 옮긴다.

```
발동     SMS 수신 (은행 번호 + "입금" 포함)
동작 1   HTTP 요청     ← 답을 response 에 담음
동작 2   알림 표시      ← response 를 꺼내 보여줌
```

**알림은 두 가지일 때만 온다.**

```
✅ 발송확정: 김지수님 450,000원 → 발송대기 (옥광 대 10kg 5)
⚠️ 확인필요: 김지수 450,000원, 후보 2건. 관리자에서 선택하세요.
```

우리 주문과 상관없는 입금(가족 송금 등)이나 읽지 못한 문자에는 **서버가 아무 답도 보내지
않는다**(HTTP 204, 본문 없음). 그때마다 폰이 울리면 정작 봐야 하는 알림을 무시하게 된다.
그런 문자도 기록은 남으니 `/admin` 맨 아래 **기타 매칭되지 않은 문자**에서 볼 수 있다.

> 빈 응답에도 빈 알림이 뜬다면, 이 동작에 **제약 조건**을 하나 걸면 된다 —
> *지역 변수 `response` 가 비어 있지 않음*.

**안 만들어도 입금 처리는 똑같이 된다.** 서버는 문자를 받는 즉시 주문을 발송대기로
넘긴다. 알림은 "잘 됐는지 아버지에게 알려주는" 편의 기능이다.
다만 `✅` 하나 보고 안심하고 넘어갈 수 있어서 만들어 두기를 권한다.


### 문자가 제대로 읽히는지 미리 확인하기

폰을 만지기 전에 컴퓨터에서 확인할 수 있다.

```bash
npm run sms -- "<새마을금고>382710**5 김지수 입금450,000 잔액1,600,000원 07/26 21:58"
```

```
  ✅ 서버가 이렇게 읽습니다
     입금액   : 450,000원
     입금자명 : 김지수
     은행     : 새마을금고
```

인자 없이 `npm run sms` 만 치면 알려진 은행 형식(새마을금고·농협·국민·카카오뱅크·신한)을
한꺼번에 점검한다.

**아버지 폰의 은행이 정해지면** 그 은행 문자를 이 명령에 넣어보면 된다.
안 읽히면 `src/lib/sms.ts` 의 규칙을 고치고 배포하면 끝 — 폰은 그대로 둔다.

### 은행 이름은 문자에서 알아서 찾는다

문자 안에 있는 은행 이름을 서버가 알아본다. 그게 **관리자 → 설정의 판매 계좌 은행과
다르면 미매칭**으로 걸러진다. 다른 계좌 입금 문자가 섞여 들어와 엉뚱한 주문이
발송대기로 올라가는 것을 막기 위해서다.

> ⚠️ 그러므로 **관리자 → 설정의 은행을 실제 판매 계좌와 똑같이** 적어야 한다.
> 설정이 `농협` 인데 새마을금고 문자가 오면 전부 미매칭이 된다.
> 표기는 관대하게 본다 — `NH농협은행`, `농협 은행`, `농협` 을 모두 같게 취급한다.

### 읽지 못한 문자는 원문이 남는다

해석에 실패하면 관리자 첫 화면의 빨간 영역에 **받은 문자 원문**이 함께 남는다.
무엇 때문에 못 읽었는지 보고 규칙을 고칠 수 있다.

확정된 건에는 원문을 남기지 않는다 — 문자에는 계좌번호와 잔액이 들어 있어
굳이 쌓아둘 이유가 없다.

### 설정이 맞는지 확인하기

**① 서버만 확인** — 컴퓨터에서 아래를 실행한다.

```bash
curl -i -X POST https://albam.web.app/api/deposit   -H "content-type: application/json"   -d '{"token":"등록한_토큰","text":"<새마을금고>382710**5 연결테스트 입금1 잔액1,000원"}'
```

| 나온 것 | 뜻 |
|---|---|
| `401` + `❌ 인증 실패` | 토큰이 틀렸다 |
| **`204 No Content`** (본문 없음) | **정상이다.** 서버까지 닿았고, 1원짜리 주문이 없어 조용히 넘어간 것 |
| `200` + `✅ 발송확정: …` | 마침 1원짜리 주문이 있었던 것. 그것도 정상 |

`-i` 를 붙여야 응답 코드가 보인다. **204는 본문이 비어 있는 것이 맞다** —
매칭 안 된 문자에는 알림을 보내지 않기 때문이다.

**② 폰까지 확인** — 진짜 입금을 기다릴 필요 없이 테스트할 수 있다.

1. 발동을 **SMS 수신 대신 `흔들기`** 로 바꾼다.
2. 동작 맨 앞에 **변수 설정** 을 넣고 문자열 변수 `sms` 에 진짜 문자를 붙여넣는다.
   (지난 입금 문자를 그대로 복사해 오면 된다)
3. HTTP 요청 본문의 `[sms_message]` 를 `[lv=sms]` 로 바꾼다.
4. 폰을 흔든다.

넣은 문자가 **진짜 주문과 맞는 것**이면 알림에 `✅ 발송확정: …` 이 뜬다.
맞는 주문이 없는 문자라면 아무 알림도 안 뜨는 것이 정상이다 —
그때는 `/admin` 맨 아래 **기타 매칭되지 않은 문자**를 펴서 방금 것이 들어왔는지 본다.
들어와 있으면 폰 → 서버까지 전부 연결된 것이다.

잘 되면 되돌린다 — 변수 설정 동작을 지우고, 본문을 `[sms_message]` 로,
발동을 `SMS 수신` 으로.

**③ 진짜로** — 본인 계좌에서 판매 계좌로 1원을 이체해 본다.
알림은 안 뜨는 것이 정상이고(1원짜리 주문이 없으니까), `/admin` 맨 아래
**기타 매칭되지 않은 문자**에 그 문자가 들어와 있으면 끝까지 연결된 것이다.


### 은행 문자를 기다리지 않고 확인하기

관리자 화면에도 테스트 도구가 있다. **설정 → 입금 문자 테스트** (`/admin/test`).
입금자명·입금액을 직접 넣어 확정/확인필요/미매칭 중 무엇이 되는지 미리 볼 수 있다.

| 버튼 | 하는 일 |
|---|---|
| **결과 미리보기** | 아무것도 바꾸지 않고 결과만 보여준다 |
| **실제로 처리** | 진짜 입금이 온 것과 똑같이 주문 상태를 바꾼다 |

기본이 미리보기인 이유: 테스트하려고 주문 상태를 실제로 바꿔 버리면 입금도 안 된 주문이
발송대기로 올라가고, 그걸 모르고 물건을 부칠 수 있다.

### 같은 문자가 두 번 와도 괜찮다

금액·이름·은행·시각(분)을 조합한 값을 문서 ID로 써서, 2분 안에 들어온 같은 입금은
자동으로 한 번만 처리된다. 두 번째 요청에는 처음과 똑같은 문구를 그대로 돌려준다.

### 예전 방식도 그대로 받는다

폰에서 이미 값을 뽑아 `name`·`amount` 로 보내던 설정도 계속 동작한다.
`text` 가 있으면 서버가 해석하고, 없으면 보내준 값을 그대로 쓴다.


## 5. 관리자 화면 쓰는 법

### 폰 홈화면에 아이콘 만들기

`/admin` 에서 브라우저 메뉴 → **홈 화면에 추가**.
앱처럼 열리고, 한 번 로그인하면 6개월간 유지된다.

### 자주 하는 일

### 관리자 화면으로 들어가는 길

주소창에 `/admin` 을 치는 것 말고, **손님 화면의 "밤 사이즈" 안내 카드를
연속으로 열 번 누르면** 관리자 화면으로 넘어간다.

아버지가 폰에서 주소를 타이핑하지 않아도 되게 만든 숨은 문이다.
**아무 표시도 나지 않는다** — 손님이 눌러도 무슨 일이 일어나는지 모른다.

마지막으로 누른 뒤 3초가 지나면 세던 횟수는 버려진다. 너무 짧으면 천천히 누르는
아버지가 열 번을 못 채우고, 너무 길면 손님이 며칠에 걸쳐 무심코 누른 것이 쌓인다.

> 예전에는 맨 위 가게 이름에 걸어 두었는데, 스크롤을 올리다 손가락이 스치는 일이
> 잦아 목록 사이의 카드로 옮겼다.

### 메뉴

위쪽 줄에 **설정 · 나가기 · 로그아웃**, 아래 줄에 매일 쓰는
**오늘 할 일 · 주문관리 · 재고관리 · 판매현황**.

아래 줄이 짧아야 지금 어느 화면인지 한눈에 들어온다. 설정은 처음 한 번 맞추면
다시 볼 일이 없고, 나가기는 손님 화면이 어떻게 보이는지 확인할 때만 쓴다
(로그아웃과 다르다 — 세션은 그대로 둔다).


| 하고 싶은 것 | 어디서 |
|---|---|
| 택배 부치고 발송 처리 | 오늘 할 일 → 보낼 주문 → 송장번호 입력 → **발송완료** |
| 보낼 주소 종이로 뽑기 | 오늘 할 일 → "보낼 주문 N건" 옆 **프린터 단추** |
| 입금이 애매할 때 | 오늘 할 일 맨 위 빨간 영역 → **입금대기 주문에서 고르기** → 주문 누르기 → 확인 창에서 **예** |
| 재고 채우기 | 재고관리 → 수량 입력 → **재고 채우기** |
| 가격 바꾸기 | 재고관리 → **자세히 고치기** |
| 사진 바꾸기 | 재고관리 → 그룹 이름 옆 **사진** (그룹 전체에 걸린다) |
| 품종 이름 바꾸기 | 재고관리 → 그룹 이름 옆 **이름** (그 그룹 상품 이름이 함께 바뀐다) |
| 상품 늘리기 | 재고관리 → 그룹 맨 아래 **+ 대보 에 상품 추가** |
| 차례 바꾸기 | 재고관리 → 왼쪽 **손잡이(⠿)** 를 눌러 위아래로 끌기 (그룹을 끌면 그룹째, 상품을 끌면 그 그룹 안에서) |
| 새 품종 들이기 | 재고관리 → 맨 아래 **새 그룹 만들기** → 그룹 이름 → 첫 상품 |
| 주소·수량·가격 고치기 | 주문관리 → 해당 주문 → 고치고 **저장하기** |
| 매출 보기 | 판매현황 |
| 환불 | 실제로 송금한 뒤 → 주문에서 환불액 적고 상태를 **환불완료** 로 |
| 교환 | 새로 보낸 뒤 → 주문 상태를 **교환완료** 로 |
| 주문 물리기 | 주문관리 → 해당 주문 → 맨 아래 **주문 삭제** (되살릴 수 있다) |
| **전화·방문 판매 넣기** | 주문관리 → **직접 넣기** |
| 계좌 바꾸기 | 설정 |

> **"취소" 상태는 없다.** 물러난 주문은 전부 **삭제**로 다룬다.
> 상태 목록에도, 주문관리의 거르기 칸에도 취소가 나오지 않는다.
>
> 주문이 물러나는 길은 셋이고 결과는 모두 같다 — 재고가 돌아오고, 손님 조회에서 사라진다.
>
> | 언제 | 누가 |
> |---|---|
> | 입금 기한이 지났을 때 | 저절로 |
> | 손님이 주문 조회에서 무를 때 | 손님 |
> | **주문 삭제** | 아버지 |
>
> 셋 다 **되살릴 수 있다.** 주문관리 → 거르기의 **삭제됨** 에서 찾아 **되살리기**.
> 되살리면 재고도 다시 잡힌다.
>
> 예전에 취소로 저장된 주문은 열어 보면 삭제된 것으로 보인다. 따로 손댈 것은 없다.

### 사이트를 거치지 않고 판 것 — 직접 넣기

전화로 받은 주문과 장터에서 만나 판 것도 **재고에서 빠져야 한다.** 안 그러면
손님 화면의 남은 수량이 실제보다 많아지고, 이미 없는 밤을 주문받게 된다.

**주문관리 → 직접 넣기** 에서 상품·수량·손님 이름만 넣으면 된다.
방문 판매라면 주소도 연락처도 비워 두어도 된다.

- 손님 주문과 **같은 길로 들어간다** — 재고 차감도 주문번호도 똑같다.
- **단가를 고칠 수 있다.** 장터에서 깎아 팔거나 아는 분께 싸게 드린 경우를 위해서다.
  손님 주문에서는 여전히 서버 가격만 쓴다 — 브라우저가 보낸 가격은 버려진다.
- 입금자와 받는 분을 따로 적는다. 같으면 체크 한 번으로 따라 채워진다
  (손님 주문서와 같은 자리, 같은 문구).
- 재고보다 많이 넣으려 하면 막히고, **무엇이 몇 개 모자란지** 알려 준다.
  재고관리에서 채운 뒤 다시 넣으면 된다.
- **이미 돈을 받았습니다** 를 켜 두면(기본) 곧바로 발송대기로 들어가고 매출에 잡힌다.
  아직 못 받았으면 꺼서 입금대기로 넣는다.
- 주문 목록에서 **직접** 이라는 표가 붙어 인터넷 주문과 구별된다.

판매현황의 **두 그래프 모두** 이 둘을 쌓아서 보여준다 — 최근 7일 매출과 상품별 판매 금액.
초록이 **인터넷 판매**, 갈색이 **직접 판매**다. 합계만 보면 사이트가 실제로
얼마나 일하고 있는지 알 수 없고, 어떤 상품이 전화로만 나가는지도 안 보인다.
주문 목록에서도 줄마다 **인터넷** / **직접** 표가 붙는다.

### 주문 상태 색

주문 목록에서 글자를 읽지 않고 색만 봐도 갈라지도록 두 가지를 같이 쓴다.
**지금 손대야 하는 것은 진하게 채우고, 끝난 것은 연하게** 둔다.

| 상태 | 색 | 뜻 |
|---|---|---|
| 입금대기 | 진한 주황 | 돈이 아직 안 들어왔다 |
| 발송대기 | 진한 초록 | **오늘 보낼 것** |
| 발송완료 | 연한 청회색 | 끝났다 |
| 환불완료 | 연한 분홍 | |
| 교환완료 | 연한 갈색 | |
| 삭제됨 | 연한 회색 | 물러난 주문 (되살릴 수 있다) |

발송완료에만 이 사이트에서 유일하게 차가운 색을 쓴다. 나머지가 전부 따뜻한 계열
(밤색·크림·주황·분홍)이라 그 안에서 회색을 만들면 입금대기와 구별되지 않았다.

### 재고에 대해

- 재고는 **주문이 들어온 순간** 빠진다. 입금 전이라도 자리를 잡아 둔다.
  무통장은 입금까지 시간이 걸리는데 그 사이 초과 판매가 나면 수습할 방법이 없기 때문이다.
- **입금이 1시간 안에 안 되면 주문이 자동으로 삭제되고 재고가 돌아온다.**
  입금하지 않은 주문이 재고를 계속 붙들고 있으면 정작 살 사람이 못 사기 때문이다.
  손님에게는 주문 화면과 완료 화면, 주문 조회에서 마감 시각을 알려 준다.

  > 기한은 `src/lib/types.ts` 의 `PAYMENT_DEADLINE_HOURS` 한 곳에서 정한다.
  > 화면 문구도 이 값을 읽으므로 숫자만 바꾸면 안내가 전부 따라간다.
  >
  > ⚠️ 1시간은 짧다. 밤에 주문하고 아침에 입금하려던 손님은 주문이 사라진다.
  > "입금했는데 주문이 없어졌다"는 전화가 오기 시작하면 이 값을 늘리는 것을 생각해 보라.
- 주문을 **삭제**하거나 **환불완료**로 바꿔도 재고가 자동으로 돌아온다.
  같은 조작을 여러 번 해도 재고가 이상해지지 않는다.
- 재고가 0이면 손님 화면에 **품절**로 뜨고 주문이 막히며, 관리자 첫 화면에서 알려 준다.
  그 전까지는 따로 알리지 않는다 — 판단할 것이 "지금 팔 수 있나 없나" 하나뿐이기 때문이다.

### 상품 사진 넣기

**사진은 상품마다가 아니라 그룹(품종)마다 정한다.** 같은 품종이면 사진이 어차피 같은데
상품마다 두면 여섯 군데를 똑같이 고쳐야 하고, 한 곳만 빠뜨리면 손님 화면에서 갈린다.

**재고관리 → 그룹 이름 옆의 [사진]** 을 누르면 `public/products/` 폴더에 있는
사진이 전부 작은 그림으로 뜬다. 하나를 누르면 **그 그룹 상품 전체에 한꺼번에** 걸린다.

> 주소를 타이핑하는 칸은 없앴다. 오타 한 글자에 깨진 그림이 뜨는데
> 아버지는 그게 왜 안 나오는지 알 방법이 없다.

> ⚠️ **폰에 찍은 사진을 여기서 바로 올릴 수는 없다.** 파일을 골라 올리는 기능이 없다.
> 사진은 아래 방법으로 `public/products/` 에 넣고 배포해야 목록에 나타난다.

#### 진짜 사진으로 바꾸기 — 컴퓨터에서 한 번만 하면 된다

**아버지가 아니라 컴퓨터를 다루는 사람이 하는 일이다.** 파일 이름을 지금 것과
똑같이 맞추면 **관리자 화면을 한 번도 손대지 않고** 사진만 갈린다.

1. 밤 사진을 찍어 컴퓨터로 옮긴다. 정사각형으로 자르고 가로 800px 정도로 줄인다.
2. **webp 로 바꿔서** `public/products/` 폴더에 넣는다 (아래 명령 참고).
   파일 이름은 한글로 둬도 된다 (`대보.webp`).
3. 배포한다.

```bash
git add -A public/products
git commit -m "사진: 실제 밤 사진으로 교체"
git push
npx firebase apphosting:rollouts:create albam -b main --project albam-416fd
```

4. 배포가 끝나면 **재고관리 → 그룹의 [사진 바꾸기]** 에서 새 사진을 고른다.
   목록은 폴더를 그때그때 읽으므로 넣은 사진이 바로 나온다.

> 파일 이름을 지금 것과 **똑같이** 맞추면 4번을 건너뛸 수 있다 (주소가 그대로라 저절로 바뀐다).
> 다만 확장자는 실제 형식과 맞춰야 한다 — 사진(jpg)을 `.svg` 이름으로 두면
> 서버가 "그림 도형 파일"이라고 알려주기 때문에 브라우저가 그리지 못한다.

> 처음에 들어 있던 임시 밤 그림(`daebo.svg` 등)은 이제 없다.
> 그 주소를 가리키는 상품이 아직 남아 있어도 읽을 때 실제 사진으로 바꿔 주므로
> 깨진 그림이 뜨지 않는다(`src/lib/products.ts` 의 `RETIRED_IMAGES`).

### 사진은 작게, webp 로

`public/` 에 넣은 파일은 **줄이지 않고 그대로** 손님 폰으로 내려간다.
폰 카메라 사진은 한 장에 5~10MB라, 그대로 두면 첫 화면이 열리는 데 몇 초씩 걸린다.

가로 1000px 정도로 줄이고 **webp** 로 담는다. 한 장이 **200KB를 넘지 않게** 하면 넉넉하다.
(`sharp` 는 Next.js 가 이미 받아 두므로 따로 설치하지 않아도 된다)

**밤 사진** — 손실 압축이 낫다. 같은 화질에 jpg 의 절반쯤 된다.

```bash
node -e "require('sharp')('원본.jpg').resize(1000).webp({quality:82}).toFile('public/products/이름.webp')"
```

**글자가 들어간 안내 그림** — 무손실로 담는다. 손실로 담으면 글자 가장자리가 번지고,
색이 몇 개 없는 그림이라 오히려 파일이 커진다(실제로 106KB → 195KB 가 됐다).

```bash
node -e "require('sharp')('원본.png').resize(1000).webp({lossless:true}).toFile('public/products/이름.webp')"
```

#### 인터넷에 올라간 사진 주소를 붙여넣기

블로그나 클라우드에 올린 사진이 있다면 주소를 그대로 넣어도 된다.
단 **사진 파일 자체의 주소**여야 한다 — `https://` 로 시작하고 `.jpg` 나 `.png` 로 끝나야 한다.
사진이 있는 *페이지* 주소를 넣으면 깨진 그림이 나온다.

> 남의 사이트에 올라간 사진을 링크로 걸면, 그쪽에서 지우는 순간 우리 사이트에서도
> 사라진다. 방법 2가 안전하다.

### 상품 이름에 대해

상품 이름이 손님 화면 표시의 **유일한 출처**다. 품종·크기·무게를 따로 입력받지 않고
`품종 크기 무게` 순으로 띄어 적으면 알아서 나뉜다.

| 이름 | 손님 화면 |
|---|---|
| `대보 중 4kg` | **대보** 묶음 → `중` 아래 `4kg` 줄 |
| `대보 특 10kg` | **대보** 묶음 → `특` 아래 `10kg` 줄 |
| `대보 중` | **대보** 묶음 → `중` 아래 한 줄 (무게 없이도 됨) |
| `꿀밤 선물세트` | **꿀밤 선물세트** 묶음 하나 |

뒤에서부터 무게(`4kg`·`10kg` 같은 `숫자+kg`) → 크기(`중`·`대`·`특`) 순으로 떼어내고
남은 앞부분을 품종으로 본다. 알아보지 못하는 이름은 통째로 묶음 이름이 되므로
새 이름을 넣어도 목록에서 사라지지 않는다.

예전 표기 `특대` 로 이름 붙인 상품이 남아 있어도 `특` 으로 알아본다(`SIZE_ALIASES`).

### 손님 화면에 보이는 차례

**두 단계로 정한다.**

```
1  대보          ← 그룹 순서
     1  4kg      ← 그 그룹 안 순서
     2  10kg
     3  4kg (대)
2  포르단
3  옥광
```

각 줄 왼쪽에 **손잡이**가 있다. 눌러서 위아래로 끌면 다른 줄들이 비켜서며 자리를
내주고, 손을 놓으면 그 자리에 앉는다.

그룹 손잡이를 끌면 **그 그룹 상품이 통째로 따라 움직인다.** 대보를 옥광 뒤로
보내려고 여섯 상품을 하나씩 옮길 일이 없다.
상품 손잡이는 **그 그룹 안에서만** 움직인다 — 위아래 끝에서 더 끌면 그냥 멈춘다.
그룹 밖으로 튀어나갈 방법이 아예 없다.

손잡이에 손가락을 올린 채로는 화면이 스크롤되지 않는다(`touch-action: none`).
줄 아무 데나 잡히게 두지 않고 손잡이를 따로 둔 이유도 같다 — 화면을 넘기려다
상품이 딸려 오면 안 된다.

**끄는 동안에는 서버를 부르지 않는다.** 손을 놓을 때 한 번만 부른다.
화면은 기다리지 않고 먼저 새 차례로 바뀌고, 서버 답이 오면 그쪽으로 맞춘다 —
저장을 기다리는 사이 줄이 제자리로 돌아갔다 다시 움직이면 "안 먹었나?" 로 보인다.
**옮길 때마다 번호를 0부터 다시 매기므로** 빈 번호나 겹친 번호가 쌓이지 않는다.

끌기가 손에 안 잡히면 손잡이에 초점을 두고 **위·아래 화살표 키**로도 한 칸씩 옮길 수 있다.

새 상품은 **제 그룹 맨 뒤에** 붙는다. 처음 보는 그룹이면 맨 뒤 그룹이 된다.

**손님 화면의 겹겹 묶음이 전부 이 이름에서 나온다.**
그래서 그룹 이름을 바꾸면 그 그룹 상품들의 이름 앞부분이 함께 갈아 끼워진다
(`대보 중 4kg` → `청실 중 4kg`). 지난 주문에 남은 상품명은 그대로 둔다 —
그때 팔린 것은 그때 이름으로 남아 있어야 무엇을 보냈는지 알 수 있다.

```
대보                ← 맨 앞 낱말 = 그룹
  중                ← 가운데 낱말 = 크기
    4kg            ← 끝 낱말 = 무게
    10kg
  대
    4kg
```

`대보 중 4kg` 과 `대보 특 10kg` 은 저절로 제자리를 찾아 들어간다.

**재고관리는 이 겹을 쓰지 않는다.** 거기서는 품종 한 겹으로만 묶고 상품을 나란히
편다. 크기로 한 겹 더 묶어 두면 상품을 끌어 옮길 때 크기 띠를 넘나드는 것이 되어
지금 어디로 가는지가 눈에 보이지 않는다. 순서를 손으로 만지는 화면이라
평평한 편이 낫고, 손님 화면은 고르기 좋아야 하니 겹겹인 편이 낫다.

그래서 **새 그룹 만들기** 는 그룹 이름을 먼저 받고, 그 이름을 앞에 붙인 채로
첫 상품 이름을 받는다 — 앞 낱말을 잘못 띄워 엉뚱한 그룹이 생기지 않도록.
그룹을 따로 저장하지 않는 이유는 같다 — 이름과 그룹이 어긋난 상품이 생기면
손님 화면과 관리자 화면이 서로 다른 말을 하게 된다.

품종·크기를 따로 입력받던 시절에는 이름만 고치면 손님 화면이 옛 이름 그대로 남는 문제가 있었다.

### 택배 부칠 때 — 주소를 종이로

**오늘 할 일 → "보낼 주문 N건" 옆 프린터 단추.** 발송대기 주문의 받는 분·연락처·주소·상품이
한 장에 나오고, 부친 것에 표시할 네모가 앞에 붙어 있다.

폰을 보며 주소를 한 건씩 옮겨 적다 한 줄을 건너뛰면 엉뚱한 곳으로 간다.
종이에 뽑아 놓고 지워 나가는 편이 빠르고 덜 틀린다.

인쇄하면 관리자 메뉴와 단추는 빠지고 주소만 남는다(`globals.css` 의 `@media print`).
**종이에서는 한 줄에 두 건씩** 들어간다 — 한 건씩 뽑으면 종이가 두 배로 든다.
화면에서는 그대로 한 줄에 한 건이라 폰으로 보기에도 좁지 않다.
한 건이 두 칸·두 장에 걸쳐 잘리지 않게 막아 두었다.

### 손님 화면이 묶이는 모양

```
[ 대보 사진 ]
      대보              ← 그룹(품종) 이름
  대보 중 4kg   28,000원
  대보 중 10kg  62,000원
  대보 대 4kg   35,000원
```

**크기로 한 겹 더 묶지 않는다.** 예전에는 품종 밑에 `중`·`대`·`특` 띠를 두고 줄에는
무게만 적었는데, 사진 밑 품종 이름을 뺀 뒤로는 그 띠가 화면에서 유일한 제목 자리가 되어
정작 품종 이름이 어디에도 안 나왔다. 줄의 `4kg` 도 무엇의 4kg인지 알 수 없었다.

각 줄에 상품 이름을 통째로 적으면 두 문제가 한꺼번에 없어지고,
장바구니·주문서에 남는 이름과도 같아져 손님이 맞게 담았는지 확인할 수 있다.
크기의 뜻은 목록 맨 위 **밤 사이즈** 안내가 맡는다.

**크기 설명은 상품마다 붙이지 않는다.** 중·대·특이 품종마다 반복되므로
목록 맨 위에서 한 번만 안내한다. 문구는 `src/lib/types.ts` 의 `SIZE_GUIDE` 에 있다.

## 6. 관리자 비밀번호 바꾸기

> **사이트 안에는 비밀번호를 바꾸는 메뉴가 없다.** 관리자 화면을 아무리 뒤져도 안 나온다.
> 비밀번호는 Firestore가 아니라 **Google Secret Manager** 라는 금고에 따로 들어 있어서,
> 사이트 코드가 읽기만 할 뿐 고칠 수 없기 때문이다.
> 사이트가 뚫려도 비밀번호는 안 새게 하려고 일부러 이렇게 나눠 놓았다.
>
> 그래서 바꾸는 곳은 **컴퓨터의 터미널** 이다. 명령 두 줄이면 끝난다.

### 1단계. 터미널 열기

VS Code에서 이 프로젝트 폴더를 연 뒤 **Ctrl + `** (숫자 1 왼쪽의 `~` 키).
메뉴로 가려면 상단 **터미널 → 새 터미널**.

아래처럼 프로젝트 경로가 보이면 준비된 것이다.

```
PS D:\Project\VSCode\bam>
```

### 2단계. 새 비밀번호 넣기

이 한 줄을 그대로 붙여넣고 Enter.

```bash
npx firebase apphosting:secrets:set albam-admin-password --project albam-416fd
```

물어보는 것에 이렇게 답한다.

| 물어보는 것 | 이렇게 |
|---|---|
| `? Enter a value for albam-admin-password` | 새 비밀번호를 치고 Enter. **화면에 아무 글자도 안 보이는 게 정상이다** (어깨너머로 못 보게) |
| `? Would you like to add this secret to apphosting.yaml?` | **No** — 이미 적혀 있다. 화살표로 No 를 고르고 Enter |

`✔ Created new secret version projects/.../versions/2` 가 나오면 성공이다.
`versions/2`, `versions/3` … 처럼 숫자가 하나씩 올라간다.

### 3단계. 사이트에 반영하기 — 이걸 빠뜨리면 안 바뀐다

2단계는 **금고에만** 새 비밀번호를 넣었을 뿐이다. 돌아가고 있는 사이트는
배포될 때 읽어 둔 **옛 비밀번호를 그대로 쥐고 있다.** 새로 배포해야 바뀐다.

```bash
npx firebase apphosting:rollouts:create albam -b main --project albam-416fd
```

`✔ Successfully created a new rollout!` 이 나온 뒤 **3~5분** 기다린다.

### 4단계. 확인

폰이나 컴퓨터에서 시크릿 창(사생활 보호 모드)으로 `/admin/login` 에 들어가
**새 비밀번호로** 로그인해 본다.

- 들어가진다 → 끝났다
- 아직 옛 비밀번호로 들어가진다 → 3단계 배포가 아직 안 끝난 것이다. 좀 더 기다린다

> **아버지 폰은 다시 로그인하지 않아도 된다.** 로그인 상태(쿠키)는 비밀번호가 아니라
> `albam-session-secret` 으로 서명해 두기 때문에, 비밀번호를 바꿔도 이미 들어가 있는
> 폰은 그대로 유지된다. 아버지가 모르는 사이에 로그아웃돼서 당황할 일이 없다.

### 어떤 비밀번호가 좋은가

이 사이트는 인터넷에 열려 있어 누구나 `/admin/login` 화면까지는 볼 수 있다.
(비밀번호를 5번 틀리면 10분 동안 막히긴 한다)

- **좋다**: `밤농사2026`, `chilgap7788` — 아버지에게 익숙한 말 + 숫자, 8자 이상
- **피한다**: 생년월일, 전화번호 뒷자리, `1234`, 가게 이름 그대로

한글도 된다. 다만 아버지 폰 자판에서 한/영 바꾸는 게 번거로우면 영문+숫자가 편하다.

### 다른 시크릿도 같은 방법이다

| 시크릿 이름 | 무엇 |
|---|---|
| `albam-admin-password` | 관리자 비밀번호 |
| `albam-macrodroid-token` | 아버지 폰이 입금 문자를 보낼 때 쓰는 열쇠 |
| `albam-session-secret` | 로그인 상태 서명 키 |

이름만 바꿔서 2단계·3단계를 똑같이 하면 된다. 단:

- `albam-macrodroid-token` 을 바꾸면 **MacroDroid 설정의 토큰도 같이 고쳐야** 한다.
  안 고치면 입금 문자가 전부 `❌ 인증 실패` 가 된다.
- `albam-session-secret` 을 바꾸면 **로그인이 전부 풀린다.** 아버지 폰도 다시 로그인해야 한다.

### 지금 값이 뭔지 잊었다면

**값은 다시 볼 수 없다.** 금고는 넣을 수만 있고 꺼내 볼 수는 없게 되어 있다.
잊었으면 위 방법으로 새로 넣으면 된다.

언제 몇 번째 버전이 만들어졌는지는 볼 수 있다.

```bash
npx firebase apphosting:secrets:describe albam-admin-password --project albam-416fd
```

### 알아 둘 만한 결정

**클라이언트는 Firestore에 직접 붙지 않는다.** 모든 데이터 접근이 서버를 거친다.
그래서 보안 규칙이 "전부 거부" 한 줄로 끝나고, 가격 조작이나 남의 주문 조회가 구조적으로 불가능하다.
`/order` 는 상품 ID와 수량만 받고 금액은 서버가 상품 문서를 다시 읽어 계산한다.

**재고 복원에 플래그를 쓰지 않는다.** "이 주문이 지금 잡고 있어야 할 재고"를 상태에서
매번 다시 계산하고 그 차이만 반영한다(`orders.ts` 의 `reservationOf`).
상태를 몇 번을 왔다 갔다 해도 이중 복원·이중 차감이 원리적으로 생기지 않는다.

**집계 테이블이 없다.** 차트와 통계는 주문 문서를 그때그때 합산한다.
1인 판매 규모라 성능 문제가 없고, 집계가 어긋나도 고칠 사람이 없기 때문이다.

**자동 정리에 스케줄러를 쓰지 않는다.** 서버가 상품 목록·주문·관리자 화면을 그릴 때
곁다리로 기한 지난 주문을 정리한다(`expireStaleOrders`). Cloud Scheduler를 붙이면
관리할 것이 하나 더 늘고, 아버지가 그게 멈춘 걸 알아챌 방법이 없다.
인스턴스당 1분에 한 번으로 제한해서 손님이 몰려도 조회가 늘지 않는다.

대신 **아무도 사이트에 들어오지 않으면 정리도 안 된다.** 손님이 목록을 보는 순간과
아버지가 관리자 화면을 여는 순간에는 항상 최신이므로 실제 운영에는 문제가 없지만,
트래픽과 무관하게 정확한 시각에 정리되어야 한다면 그때 Cloud Scheduler를 붙이면 된다.
