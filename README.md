# 칠갑산 석촌 햇 밤 — 무통장 입금 전용 밤 판매 사이트

충남 칠갑산 석촌에서 유기농 햇밤(대보·포르단·옥광)을 파는 1인 판매자용 사이트다.
카드 결제 없이 **무통장 입금만** 받고, 입금 확인을 **사람이 대조하지 않는다**.

운영자가 기술에 익숙하지 않다는 전제로 만들었다. 그래서 대부분의 설계가
"손이 덜 가는 쪽"이 아니라 **"틀렸을 때 손으로 수습할 일이 없는 쪽"** 으로 기울어 있다.

| | |
|---|---|
| 배포 주소 | `https://albam--albam-416fd.us-central1.hosted.app` |
| 호스팅 | Firebase App Hosting (Blaze) — GitHub push 시 자동 빌드 |
| 저장소 | Firestore (프로덕션 모드) |
| 프레임워크 | Next.js 15 (App Router) · TypeScript · Tailwind CSS v4 |

## 1. 어떻게 돌아가는가

### 입금이 자동으로 확인되는 흐름

```
손님 주문          아버지 폰                     서버
──────────         ──────────                    ──────────
주문서 작성   →    (입금대기 주문 생성)
계좌로 입금   →    은행 입금 문자 도착
                   MacroDroid가 문자를
                   **통째로** 전달
                          │
                          └─ POST /api/deposit ─→  문자에서 금액·이름·은행을 뽑고
                                                   같은 이름 + 같은 금액의
                                                   입금대기 주문을 찾는다
                                                        │
                   알림으로 결과 표시  ←──────────────────┤
                                              1건  → 발송대기로 확정
                                              여러 건 → 확인필요 (관리자가 선택)
                                              0건  → 미매칭 (관리자가 연결)
```

**문자 해석은 서버가 한다.** 폰은 받은 문자를 그대로 넘기기만 하므로
MacroDroid 설정에 정규식도 변수도 없다.

문자 형식은 은행마다 다르고 언제든 바뀐다. 해석 규칙을 폰에 두면 그때마다
아버지 폰을 직접 받아서 고쳐야 하지만, 서버에 두면 코드를 고쳐 배포하면 끝이다.
읽지 못한 문자는 원문이 관리자 화면에 남아 무엇 때문에 실패했는지 볼 수 있고,
`npm run sms` 로 실제 은행 문자를 넣어 규칙을 미리 검증할 수도 있다.


### 손대야 하는 것이 생기면 첫 화면에 뜬다

관리자 첫 화면(`/admin`)은 위에서부터 **급한 순서**로 쌓여 있다.

1. 🔴 **확인이 필요한 입금** — 돈은 들어왔는데 주문이 안 움직이고 있는 건
2. 🟠 **매진** — 손님이 지금 주문할 수 없는 상품
3. 📦 **보낼 주문** — 송장번호 넣고 [발송완료] 누르면 끝
4. 📊 판매 현황과 차트

## 2. 로컬에서 돌려보기

Firestore 에뮬레이터를 쓰므로 **실제 데이터를 건드리지 않고 과금도 없다.**
(에뮬레이터에는 Java가 필요하다)

```bash
npm install
cp .env.local.example .env.local

npm run emulators   # 터미널 1 — Firestore 에뮬레이터
npm run seed        # 터미널 2 — 상품 18종 + 기본 설정 넣기
npm run dev         # http://localhost:3000
```

관리자 로그인 비밀번호는 `.env.local` 의 `ADMIN_PASSWORD` (기본 `test1234`).

### 확인용 명령

```bash
npm run smoke   # 가격 재계산·입금 매칭·자동 취소·재고 복원 등 핵심 로직 123가지 점검
npx tsc --noEmit
npm run build
```

`npm run smoke` 는 에뮬레이터에서만 돌아간다(실 데이터 삭제 사고 방지).
주문/입금 컬렉션을 비우고 다시 채우므로 **운영 데이터에는 절대 쓰지 말 것.**

## 3. 처음 배포하기

### 3-1. GitHub에 올리기

```bash
git remote add origin https://github.com/skellee80/albam.git
git branch -M main
git push -u origin main
```

### 3-2. 시크릿 3개 등록

비밀번호와 토큰은 소스에 두지 않는다. Secret Manager에 넣고 `apphosting.yaml` 이 이름으로 참조한다.

```bash
firebase login
firebase use albam-416fd

firebase apphosting:secrets:set albam-admin-password     # 관리자 비밀번호
firebase apphosting:secrets:set albam-session-secret     # 세션 서명 키 (아래 참고)
firebase apphosting:secrets:set albam-macrodroid-token   # MacroDroid 인증 토큰
```

`albam-session-secret` 과 `albam-macrodroid-token` 은 사람이 외울 필요가 없다.
길고 무작위인 값을 쓴다:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

> **관리자 비밀번호만** 아버지가 기억할 수 있는 값으로 정한다.
> 폰에서는 한 번만 입력하면 6개월간 유지된다.

### 3-3. App Hosting 백엔드 만들기

```bash
firebase apphosting:backends:create --project albam-416fd
```

물어보는 대로 고르면 된다.

- 리전: `us-central1`
- GitHub 저장소: `skellee80/albam` (Firebase GitHub 앱 권한 승인 필요)
- 라이브 브랜치: `main`
- 백엔드 ID: `albam`

이후 `main` 에 push할 때마다 자동으로 빌드·배포된다.

### 3-4. Firestore 규칙과 인덱스 올리기

```bash
firebase deploy --only firestore:rules,firestore:indexes
```

> **보안 규칙은 모든 클라이언트 접근을 막는다.** 실수가 아니다.
> 이 앱은 브라우저에서 Firestore에 직접 붙지 않고, 모든 읽기·쓰기를 서버(Admin SDK)가 한다.
> 덕분에 규칙을 잘못 써서 주문·연락처·주소가 새어 나갈 경로 자체가 없다.

### 3-5. 첫 데이터 넣기

배포 후 `/admin` 에 들어가

1. **설정** 에서 입금 계좌와 문의 전화번호를 실제 값으로 바꾼다.
2. **상품·재고** 에서 가격과 재고를 실제 값으로 채운다.

상품 18종(품종 3 × 크기 3 × 무게 2)을 코드로 한 번에 넣으려면, `.env.local` 에서
`FIRESTORE_EMULATOR_HOST` 를 지우고 `gcloud auth application-default login` 후
`npm run seed` 를 돌린다. 가격과 사진은 **임시값**이므로 관리자 화면에서 바꿔야 한다.

> 이름 규칙이 바뀌어 예전 이름의 상품이 남아 있다면 `npm run seed -- --replace` 로
> 상품을 전부 지우고 새로 넣을 수 있다. 주문 기록은 건드리지 않는다.

## 4. MacroDroid 설정 (아버지 폰)

이 부분이 사이트에서 가장 중요하다. 한 번 맞춰 놓으면 다시 손댈 일이 없다.

**폰은 문자를 통째로 보내기만 한다.** 금액과 이름을 뽑는 일은 서버가 한다.
그래서 폰에는 정규식도 변수도 없고, 은행이 바뀌어도 **아버지 폰을 다시 만질 필요가 없다**
— 서버 코드(`src/lib/sms.ts`)만 고쳐 배포하면 된다.

### 1단계. 트리거 — 언제 매크로가 돌게 할 것인가

MacroDroid 앱 → 아래 `+` → **매크로 추가** → 트리거의 `+`

1. **연결** → **SMS 수신** 을 고른다.
2. **발신자**: 은행 문자가 오는 번호를 넣는다. (문자 앱에서 확인. 예: `15881111`)
3. **내용 필터**: `입금` 을 넣는다.

> 내용 필터가 없어도 서버가 출금 문자를 걸러내지만, 폰에서 미리 거르면
> 쓸데없는 요청과 알림이 줄어든다.

### 2단계. 서버로 보내기

동작(작업)의 `+` → **연결** → **HTTP 요청**

| 항목 | 값 |
|---|---|
| 방식 | `POST` |
| URL | `https://albam--albam-416fd.us-central1.hosted.app/api/deposit` |
| 콘텐츠 타입 | `application/json` |
| 본문 | 아래 |

```json
{"token":"등록한_MACRODROID_토큰","text":"[sms_message]"}
```

`[sms_message]` 는 직접 타이핑하지 말고 **매직 텍스트 버튼**에서 고른다.

같은 화면에서 **응답을 변수에 저장** 을 켜고 변수 이름을 `response` 로 둔다.

### 3단계. 결과를 알림으로 보기

동작의 `+` → **알림** → **알림 표시**

| 항목 | 값 |
|---|---|
| 제목 | `입금 확인` |
| 본문 | `[lv=response]` (매직 텍스트 → 변수) |

이제 입금 문자가 올 때마다 이런 알림이 뜬다.

```
✅ 확정: 김지수님 450,000원 → 발송대기 (옥광 대 10kg 5)
⚠️ 확인필요: 김지수 450,000원, 후보 2건. 관리자에서 선택하세요.
❓ 미매칭: 김지수 450,000원. 관리자에서 확인하세요.
❓ 문자를 읽지 못했습니다: 입금자명을 찾지 못했습니다. 관리자에서 확인하세요.
```

`✅` 면 아무것도 안 해도 된다. 나머지는 `/admin` 첫 화면에서 처리한다.

**설정은 이게 전부다.** 동작 두 개, 트리거 하나.

### 문자가 제대로 읽히는지 미리 확인하기

폰을 만지기 전에 컴퓨터에서 확인할 수 있다.

```bash
npm run sms -- "<새마을금고>382710**5 김지수 입금450,000 잔액1,600,000원 07/26 21:58"
```

```
  ✅ 서버가 이렇게 읽습니다
     입금액   : 450,000원
     입금자명 : 김지수
     은행     : 새마을금고
```

인자 없이 `npm run sms` 만 치면 알려진 은행 형식(새마을금고·농협·국민·카카오뱅크·신한)을
한꺼번에 점검한다.

**아버지 폰의 은행이 정해지면** 그 은행 문자를 이 명령에 넣어보면 된다.
안 읽히면 `src/lib/sms.ts` 의 규칙을 고치고 배포하면 끝 — 폰은 그대로 둔다.

### 은행 이름은 문자에서 알아서 찾는다

문자 안에 있는 은행 이름을 서버가 알아본다. 그게 **관리자 → 설정의 판매 계좌 은행과
다르면 미매칭**으로 걸러진다. 다른 계좌 입금 문자가 섞여 들어와 엉뚱한 주문이
발송대기로 올라가는 것을 막기 위해서다.

> ⚠️ 그러므로 **관리자 → 설정의 은행을 실제 판매 계좌와 똑같이** 적어야 한다.
> 설정이 `농협` 인데 새마을금고 문자가 오면 전부 미매칭이 된다.
> 표기는 관대하게 본다 — `NH농협은행`, `농협 은행`, `농협` 을 모두 같게 취급한다.

### 읽지 못한 문자는 원문이 남는다

해석에 실패하면 관리자 첫 화면의 빨간 영역에 **받은 문자 원문**이 함께 남는다.
무엇 때문에 못 읽었는지 보고 규칙을 고칠 수 있다.

확정된 건에는 원문을 남기지 않는다 — 문자에는 계좌번호와 잔액이 들어 있어
굳이 쌓아둘 이유가 없다.

### 설정이 맞는지 확인하기

**① 서버만 확인** — 컴퓨터에서 아래를 실행한다.
`❌ 인증 실패` 면 토큰이 틀린 것이고, `❓ 미매칭` 이면 연결은 정상이다.

```bash
curl -X POST https://albam--albam-416fd.us-central1.hosted.app/api/deposit \
  -H "content-type: application/json" \
  -d '{"token":"등록한_토큰","text":"<새마을금고>382710**5 연결테스트 입금1 잔액1,000원"}'
```

**② 폰까지 확인** — 진짜 입금을 기다릴 필요 없이 테스트할 수 있다.

1. 트리거를 **SMS 수신 대신 `흔들기`** 로 바꾼다.
2. 동작 맨 앞에 **변수 설정** 을 넣고 문자열 변수 `sms` 에 진짜 문자를 붙여넣는다.
3. HTTP 요청 본문의 `[sms_message]` 를 `[lv=sms]` 로 바꾼다.
4. 폰을 흔든다. 알림에 서버 응답이 그대로 뜬다.

잘 되면 되돌린다 — 변수 설정 동작을 지우고, 본문을 `[sms_message]` 로,
트리거를 `SMS 수신` 으로.

**③ 진짜로** — 본인 계좌에서 판매 계좌로 1원을 이체해 본다.
`❓ 미매칭` 이 뜨면 문자 → 서버까지 전부 연결된 것이다
(1원짜리 주문이 없으니 미매칭이 정상이다).

### 은행 문자를 기다리지 않고 확인하기

관리자 화면에도 테스트 도구가 있다. **설정 → 입금 문자 테스트** (`/admin/test`).
입금자명·입금액을 직접 넣어 확정/확인필요/미매칭 중 무엇이 되는지 미리 볼 수 있다.

| 버튼 | 하는 일 |
|---|---|
| **결과 미리보기** | 아무것도 바꾸지 않고 결과만 보여준다 |
| **실제로 처리** | 진짜 입금이 온 것과 똑같이 주문 상태를 바꾼다 |

기본이 미리보기인 이유: 테스트하려고 주문 상태를 실제로 바꿔 버리면 입금도 안 된 주문이
발송대기로 올라가고, 그걸 모르고 물건을 부칠 수 있다.

### 같은 문자가 두 번 와도 괜찮다

금액·이름·은행·시각(분)을 조합한 값을 문서 ID로 써서, 2분 안에 들어온 같은 입금은
자동으로 한 번만 처리된다. 두 번째 요청에는 처음과 똑같은 문구를 그대로 돌려준다.

### 예전 방식도 그대로 받는다

폰에서 이미 값을 뽑아 `name`·`amount` 로 보내던 설정도 계속 동작한다.
`text` 가 있으면 서버가 해석하고, 없으면 보내준 값을 그대로 쓴다.


## 5. 관리자 화면 쓰는 법

### 폰 홈화면에 아이콘 만들기

`/admin` 에서 브라우저 메뉴 → **홈 화면에 추가**.
앱처럼 열리고, 한 번 로그인하면 6개월간 유지된다.

### 자주 하는 일

| 하고 싶은 것 | 어디서 |
|---|---|
| 택배 부치고 발송 처리 | 첫 화면 → 보낼 주문 → 송장번호 입력 → **발송완료** |
| 입금이 애매할 때 | 첫 화면 맨 위 빨간 영역 → **입금대기 주문에서 고르기** → 주문 누르기 → 확인 창에서 **예** |
| 재고 채우기 | 상품·재고 → 수량 입력 → **재고 채우기** |
| 주소·수량·가격 고치기 | 주문 → 해당 주문 → 고치고 **저장하기** |
| 환불 | 실제로 송금한 뒤 → 주문에서 환불액 적고 상태를 **환불완료** 로 |
| 교환 | 새로 보낸 뒤 → 주문 상태를 **교환완료** 로 |
| 계좌 바꾸기 | 설정 |

### 재고에 대해

- 재고는 **주문이 들어온 순간** 빠진다. 입금 전이라도 자리를 잡아 둔다.
  무통장은 입금까지 시간이 걸리는데 그 사이 초과 판매가 나면 수습할 방법이 없기 때문이다.
- **입금이 24시간 안에 안 되면 주문이 자동으로 취소되고 재고가 돌아온다.**
  입금하지 않은 주문이 재고를 계속 붙들고 있으면 정작 살 사람이 못 사기 때문이다.
  손님에게는 주문 화면과 완료 화면, 주문 조회에서 마감 시각을 알려 준다.
- 주문을 **취소**하거나 **환불완료**로 바꿔도 재고가 자동으로 돌아온다.
  같은 조작을 여러 번 해도 재고가 이상해지지 않는다.
- 재고가 0이면 손님 화면에 **품절**로 뜨고 주문이 막히며, 관리자 첫 화면에서 알려 준다.
  그 전까지는 따로 알리지 않는다 — 판단할 것이 "지금 팔 수 있나 없나" 하나뿐이기 때문이다.

### 상품 이름에 대해

상품 이름이 손님 화면 표시의 **유일한 출처**다. 품종·크기·무게를 따로 입력받지 않고
`품종 크기 무게` 순으로 띄어 적으면 알아서 나뉜다.

| 이름 | 손님 화면 |
|---|---|
| `대보 중 4kg` | **대보** 묶음 → `중` 아래 `4kg` 줄 |
| `대보 특 10kg` | **대보** 묶음 → `특` 아래 `10kg` 줄 |
| `대보 중` | **대보** 묶음 → `중` 아래 한 줄 (무게 없이도 됨) |
| `꿀밤 선물세트` | **꿀밤 선물세트** 묶음 하나 |

뒤에서부터 무게(`4kg`·`10kg` 같은 `숫자+kg`) → 크기(`중`·`대`·`특`) 순으로 떼어내고
남은 앞부분을 품종으로 본다. 알아보지 못하는 이름은 통째로 묶음 이름이 되므로
새 이름을 넣어도 목록에서 사라지지 않는다.

예전 표기 `특대` 로 이름 붙인 상품이 남아 있어도 `특` 으로 알아본다(`SIZE_ALIASES`).

품종·크기를 따로 입력받던 시절에는 이름만 고치면 손님 화면이 옛 이름 그대로 남는 문제가 있었다.

### 손님 화면이 묶이는 모양

```
대보                 ← 품종
  중                 ← 크기
    4kg   28,000원
    10kg  62,000원
  대
    4kg   35,000원
    10kg  78,000원
```

무게를 바깥으로 올려 "대보 4kg" / "대보 10kg" 로 나누면 같은 품종이 두 번 나온다.
손님은 품종을 먼저 고르고 그다음 크기와 양을 정하므로, 고르는 순서대로 겹쳐 둔다.

**크기 설명은 상품마다 붙이지 않는다.** 중·대·특이 품종마다 반복되므로
목록 맨 위에서 한 번만 안내한다. 문구는 `src/lib/types.ts` 의 `SIZE_GUIDE` 에 있다.

## 6. 시크릿 바꾸기

관리자 비밀번호나 MacroDroid 토큰을 바꿀 때:

```bash
firebase apphosting:secrets:set albam-admin-password
```

새 버전이 만들어지고, **다음 배포부터** 적용된다. 바로 반영하려면 빈 커밋을 밀어 재배포한다.

```bash
git commit --allow-empty -m "chore: 시크릿 갱신 반영"
git push
```

`albam-session-secret` 을 바꾸면 기존 로그인 세션이 모두 풀려서 다시 로그인해야 한다.

### 알아 둘 만한 결정

**클라이언트는 Firestore에 직접 붙지 않는다.** 모든 데이터 접근이 서버를 거친다.
그래서 보안 규칙이 "전부 거부" 한 줄로 끝나고, 가격 조작이나 남의 주문 조회가 구조적으로 불가능하다.
`/order` 는 상품 ID와 수량만 받고 금액은 서버가 상품 문서를 다시 읽어 계산한다.

**재고 복원에 플래그를 쓰지 않는다.** "이 주문이 지금 잡고 있어야 할 재고"를 상태에서
매번 다시 계산하고 그 차이만 반영한다(`orders.ts` 의 `reservationOf`).
상태를 몇 번을 왔다 갔다 해도 이중 복원·이중 차감이 원리적으로 생기지 않는다.

**집계 테이블이 없다.** 차트와 통계는 주문 문서를 그때그때 합산한다.
1인 판매 규모라 성능 문제가 없고, 집계가 어긋나도 고칠 사람이 없기 때문이다.

**자동 취소에 스케줄러를 쓰지 않는다.** 서버가 상품 목록·주문·관리자 화면을 그릴 때
곁다리로 기한 지난 주문을 정리한다(`expireStaleOrders`). Cloud Scheduler를 붙이면
관리할 것이 하나 더 늘고, 아버지가 그게 멈춘 걸 알아챌 방법이 없다.
인스턴스당 1분에 한 번으로 제한해서 손님이 몰려도 조회가 늘지 않는다.

대신 **아무도 사이트에 들어오지 않으면 정리도 안 된다.** 손님이 목록을 보는 순간과
아버지가 관리자 화면을 여는 순간에는 항상 최신이므로 실제 운영에는 문제가 없지만,
트래픽과 무관하게 정확한 시각에 취소되어야 한다면 그때 Cloud Scheduler를 붙이면 된다.
